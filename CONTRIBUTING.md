# Contributing to BOSC Community Library

Thank you for contributing to BOSC Community Library. This project follows an incremental open-source workflow, so every contribution should be clear, reviewable, and well documented.

## Before You Start

- Read [README.md](README.md) for project context
- Review [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) before participating
- Check open issues or create one before starting a significant change
- Keep Day 1 contributions focused on repository setup and foundation work

## Branch Naming Conventions

Use descriptive branch names based on the type of work:

- `feat/short-description`
- `fix/short-description`
- `docs/short-description`
- `chore/short-description`
- `test/short-description`

Examples:

- `docs/update-readme`
- `feat/base-landing-page`
- `chore/add-github-templates`

## Commit Message Standards

Write commits in the imperative mood and keep them short, specific, and professional.

Recommended format:

```text
type: concise summary
```

Examples:

- `chore: initialize repository structure`
- `docs: add community contribution guidelines`
- `feat: create responsive landing page`
- `chore: add GitHub issue and PR templates`

Guidelines:

- Keep the subject line under 72 characters when possible
- Make one logical change per commit
- Avoid vague messages such as `update files` or `fix stuff`

## Contribution Workflow

1. Fork the repository or create a branch from `main`
2. Sync with the latest project state before editing
3. Create a focused branch using the naming rules above
4. Make small, reviewable commits with clear messages
5. Test changes locally
6. Update documentation when behavior or workflow changes
7. Open a pull request using the repository template

## Pull Request Process

Before opening a pull request:

- Re-read your changes for clarity and consistency
- Confirm the application still runs on localhost
- Check that markdown files render cleanly on GitHub
- Verify that your branch contains only relevant changes

Pull requests should include:

- A short summary of the purpose
- A list of notable changes
- Testing notes
- Screenshots for UI changes when applicable
- Links to related issues or tasks

## Code Formatting Standards

Follow these formatting rules across the repository:

- Use semantic HTML elements
- Use consistent indentation with 2 spaces for HTML, CSS, and JavaScript
- Prefer readable class names and clear section labels
- Keep CSS organized by layout, components, and responsive behavior
- Write JavaScript that is minimal, readable, and progressive
- Avoid placeholder content and unreviewed generated text

## Reporting Issues

Use the GitHub issue templates whenever possible:

- `bug_report.md` for defects or regressions
- `feature_request.md` for proposed enhancements

When reporting an issue, include:

- A clear title
- The current behavior
- The expected behavior
- Steps to reproduce, if relevant
- Browser, device, or environment details

## Review Expectations

Contributors and reviewers should aim for:

- Respectful and constructive feedback
- Attention to accessibility and maintainability
- Clear rationale for requested changes
- Documentation updates when new behavior is introduced

## Questions and Support

If a requirement is unclear, open an issue or start a discussion before implementing a large change. Early communication helps keep the project healthy and realistic across the full development schedule.
